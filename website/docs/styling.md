# Customizing Styles

## How the Plugin Works

`velvetThunder.plugin()` generates **structural** CSS for all `velvet-*` component classes — layout, sizing, spacing, transitions, and disabled cursors. Colors, borders, and hover/focus states are intentionally left out. This is what makes Velvet Thunder semi-headless: the plugin gives components their shape, and you give them their look.

The plugin also adds `.velvet-outline` and `.velvet-outline-offset-0` utility classes used internally for focus rings (see [Outline](./utilities/outline.md)).

### Tailwind v3

The plugin safelists all `/^velvet-/` classes so Tailwind never purges them, even when they are composed dynamically at runtime.

### Tailwind v4

The safelist is not respected in Tailwind v4. Instead, `velvetThunder.content()` points Tailwind at the compiled component files so it can detect which classes are used. Classes that are composed dynamically at runtime (e.g. `velvet-button-${size}`) will not appear as literal strings in those files and may be omitted from the output. Explicitly use every variant class you need somewhere in your own templates, or write them out in your stylesheet, to ensure they are included.

## Opting Out of Components

Pass `false` for any component to skip generating its structural styles:

```js
velvetThunder.plugin({
  components: {
    button: false,
  },
});
```

## Adding Visual Styles

There are two ways to style a component: write CSS by hand, or have the plugin generate it from CSS custom properties. Both target the same classes, so you can freely combine them — use generated colors where they fit and hand-written CSS for anything else. If a generated default is too restrictive for one case, just target that class with your own CSS and override it.

### Writing CSS by Hand

Create a CSS file and target the `velvet-*` classes. Use `@apply` to compose Tailwind utilities, or write plain CSS.

The class naming convention is:

- `.velvet-{component}` — the root element
- `.velvet-{component}-{variant}` — a named variant (`primary`, `secondary`, `ghost`, …)
- `.velvet-{component}-{state}` — a state modifier (`disabled`, `invalid`, …)
- `.velvet-{component}-{part}` — a sub-element of a compound component

#### Example: Tag

The `VelvetTag` component applies `.velvet-tag`, `.velvet-tag-{size}`, and `.velvet-tag-{variant}` to its root element. `.velvet-tag` itself is always present, so it's the place to target styles that should apply no matter the variant — for example, a different border radius:

```css
.velvet-tag {
  @apply rounded-full;
}
```

To style the `primary` and `secondary` variants specifically:

```css
.velvet-tag-primary {
  @apply bg-violet-500 text-white;
}

.velvet-tag-secondary {
  @apply bg-violet-500/20 text-violet-600;
}
```

Because `@variant` accepts any string, you can also introduce entirely new variants this way — just pass the name as `@variant` and add a matching CSS class.

All other components follow a similar pattern, you can look at the rendered output in each components demo page to see which classes can be targeted.

### Generating Colors from CSS Variables

Instead of writing CSS by hand, some components can generate their colors from CSS custom properties. Each component's own page lists whether it supports this and exactly which custom properties it reads, under "Generated Colors".

#### The `variants` option

For components with named variants, pass `variants` to generate their colors:

```js
velvetThunder.plugin({
  components: {
    button: { variants: [true] },
  },
});
```

This generates the `primary`/`secondary`/`ghost` classes reading from matching custom properties, so:

```css
:root {
  --velvet-primary: #0d9488;
  --velvet-primary-hover: #0f766e;
  --velvet-primary-active: #115e59;
  --velvet-primary-disabled: #99f6e4;
  --velvet-on-primary: #ffffff;
}
```

...is enough to style `.velvet-button-primary` without writing any CSS for it. To generate a different set of names, pass them explicitly: `variants: [true, ['brand']]`.

#### The `colors` option

Components with no variant to choose between — just one look to turn on — use a plain boolean instead:

```js
velvetThunder.plugin({
  components: {
    checkbox: { colors: true },
  },
});
```

This makes the checkbox read the same `--velvet-primary` variable defined above for its checked/focus color — so one set of variables tends to drive the whole library's look, not just one component at a time.

## Live Theme Preview

The theme toggle in the header of this site is a live demonstration of the semi-headless split described above. It switches between separate stylesheets:

- **Default** loads the violet visual skin used throughout these docs — colors, borders, and hover/focus states layered on top of the structural classes, written with plain `@apply` CSS.
- **Unstyled** removes any skin entirely, leaving only the structural CSS generated by `velvetThunder.plugin()`. Components stay laid out and sized correctly, but have no color or visual styling of their own.
- **CSS Variables** uses the `variants`/`colors` options described above: it loads a small stylesheet that only defines `--velvet-*` custom properties, and the plugin-generated classes pick up their colors from those.

**None of these skins are part of the `velvet-thunder` addon.** As shipped, the library is entirely unstyled — every visual look, including the ones used on this site, is something you write yourself (either as plain CSS, or via the `variants`/`colors` options above). These themes are only this documentation site's own examples of what that can look like.

You can find the CSS that defines them on GitHub:

- The **Default** skin: [`website/tailwind/components/`](https://github.com/Bagaar/velvet-thunder/tree/main/website/tailwind/components) — one file per component, following the same class-targeting pattern described above.
- The **CSS Variables** skin: [`website/tailwind/themes/variables.css`](https://github.com/Bagaar/velvet-thunder/blob/main/website/tailwind/themes/variables.css) — just the custom property definitions, plus the `variants`/`colors` options enabled in [`website/tailwind.config.variables.js`](https://github.com/Bagaar/velvet-thunder/blob/main/website/tailwind.config.variables.js) (kept separate from [`website/tailwind.config.js`](https://github.com/Bagaar/velvet-thunder/blob/main/website/tailwind.config.js) so these generated classes only ever end up in the "CSS Variables" theme's own build, not the always-loaded base stylesheet).
- The plugin-side generators themselves: [`velvet-thunder/tailwind/variants.cjs`](https://github.com/Bagaar/velvet-thunder/blob/main/velvet-thunder/tailwind/variants.cjs) (the shared `generateVariants`/`whenColorsEnabled` helpers) and each component file under [`velvet-thunder/tailwind/components/`](https://github.com/Bagaar/velvet-thunder/tree/main/velvet-thunder/tailwind/components) (what those helpers actually generate, per component).
